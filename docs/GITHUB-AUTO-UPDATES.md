# Public GitHub Release auto-updates (v0.14.0)

## First-time setup

1. Install **v0.14.0** manually on each WordPress site currently running an older version. An older version has no GitHub updater and cannot discover this upgrade by itself.
2. Back up WordPress files and the database. Test on staging before production.
3. On the site, go to **Achuthan Jobs > Settings** and ensure **Automatically install verified Achuthan Jobs GitHub releases** is enabled (administrators only). Enabled by default after upgrading.
4. Confirm outgoing HTTPS requests to `api.github.com` and `github.com`, WP-Cron/background updates, and writable `wp-content/plugins`.
5. In **Dashboard > Updates**, click **Check Again** to refresh. Background installation uses WordPress's own scheduler and can be delayed.

## Every future release (public repo)

1. Merge code changes into `main`, increment **both** `Version:` and `Achuthan_Jobs::VERSION` in `plugin/achuthan-jobs/achuthan-jobs.php` (e.g., `0.15.0`). Update docs and test.
2. Create and push tag `v0.15.0` on the matching commit; `.github/workflows/release.yml` validates the version, builds the plugin ZIP and publishes the **non-prerelease GitHub Release** with asset **`achuthan-jobs.zip`**.
3. Check https://github.com/MohanaAchuthan30/achuthan-jobs/releases/latest . It must contain `achuthan-jobs.zip`, not only GitHub's autogenerated Source Code ZIP. The archive must contain `achuthan-jobs/achuthan-jobs.php` at its root.
4. WordPress discovers the newer release on scheduled checks (typically up to 12 hours plus WP-Cron delay). It downloads the official ZIP, verifies SHA-256 against GitHub's asset digest, and installs via the native WordPress plugin upgrader.

**GitHub web-only workflow:** In **Releases → Draft a new release**, create tag `vX.Y.Z` pointing to the matching versioned commit, choose **Publish release**, then check the GitHub Actions **Publish public GitHub Release** workflow. It uploads or replaces the `achuthan-jobs.zip` asset for that release. If the workflow fails, correct the problem before expecting updates on installed sites. Do not use the generated Source Code ZIP as the plugin package.

### Important limits
- **Regular pushes, commits, pull requests, and prereleases do not update websites.** Only the latest published release with valid version/ZIP/checksum can update them.
- If GitHub's unauthenticated API returns 404 or the repository cannot be accessed publicly, updates cannot be discovered. Confirm GitHub visibility while logged out. Rate limits can also delay checks.
- The ZIP must keep the folder `achuthan-jobs` and main plugin file name exactly. Existing WordPress jobs and applications live in the WordPress database and are not intentionally overwritten by plugin file upgrades; backups are still essential.
- Automatic update can fail when WordPress background updates are disabled, a network filter blocks GitHub, the host requires FTP login, disk space is insufficient, or WP-Cron is not running.
- Do not post sensitive candidate records, API keys, or other secrets in a public repository.
- Public visibility is not the same as open-source licensing; review rights and upstream dependencies before publishing proprietary source code.

### Troubleshooting
- GitHub Release unavailable? Test https://api.github.com/repos/MohanaAchuthan30/achuthan-jobs/releases/latest from a browser; HTTP 404 means missing/inaccessible published release.
- Update not showing? Wait for cached checks (positive cache 4h, error 20m), and use **Dashboard > Updates > Check Again**. Do not edit the plugin PHP files directly on production.
- Version does not match? Keep `vX.Y.Z` Git tag, plugin header `X.Y.Z`, and class constant `X.Y.Z` consistent.
- Troubleshoot first on a staging site and check WordPress Site Health / server logs.
